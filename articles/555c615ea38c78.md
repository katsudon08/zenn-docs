## はじめに

先日、チームメンバーのターミナル操作を横で見ていたときに `mise` というコマンドを叩いているのに気づきました。「それ何ですか？」と聞いたのがきっかけで、自分でも調べてみたところ、これまで複数のツールを使い分けてやっていたことが、ほぼこれ1つで片付くと分かりました。

これまでの自分は、Node のバージョンは nvm、環境変数の読み込みは別の仕組み、よく使うコマンドは Makefile や npm scripts、というふうにツールがバラバラでした。新しいプロジェクトに入るたびに「このプロジェクトは何で何を管理しているんだっけ」と確認するのが地味に面倒だったのです。

この記事では、具体的な設定方法を細かく追うというより、**mise で何ができるのか**、そして**何のために導入するのか**に絞って整理します。

## mise とは

mise（「ミーズ」と読みます。以前は rtx という名前でした）は、ひとことで言えば**開発環境まわりをまとめて面倒見てくれるツール**です。Rust で書かれていて動作が速いのも特徴です。

これまで別々のツールでやっていた3つの役割を、mise は1つで肩代わりします。

| 役割 | これまで使っていたツール | mise |
|---|---|---|
| 言語・ツールのバージョン管理 | nvm / pyenv / rbenv / asdf | ✅ |
| 環境変数の管理 | direnv / dotenv | ✅ |
| タスク実行（コマンドのショートカット） | make / npm scripts | ✅ |

設定はプロジェクト直下に置く `mise.toml` という1ファイルにまとめます。たとえば最小構成はこんな形です。

```toml
[tools]
node = "20"
python = "3.12"

[env]
DATABASE_URL = "postgres://localhost/myapp"

[tasks.dev]
run = "npm run dev"
```

このファイルを見れば「このプロジェクトは Node 20 と Python 3.12 で動く」とひと目で分かります。ここからは、3つの役割がそれぞれどんな困りごとを解決してくれるのかを順に見ていきます。

## 1. バージョン管理：プロジェクトごとに自動で切り替わる

一番うれしいのがこれです。

複数のプロジェクトを行き来していると、「プロジェクト A は Node 18、プロジェクト B は Node 20」のように、要求されるバージョンがバラバラになりがちです。nvm を使っていると、ディレクトリを移動するたびに `nvm use 18` と打ち直す必要があり、忘れたまま作業してエラーで気づく、ということがよくありました。

mise はシェルに組み込んで使うため、**該当ディレクトリに `cd` しただけで、そのプロジェクトに書かれたバージョンへ自動で切り替わります**。

```bash
cd project-a   # Node 18 になる
cd ../project-b # Node 20 に切り替わる
```

しかも対象は Node だけではありません。Python、Ruby、Go、Terraform、各種 CLI ツールまで、同じ仕組みでまとめて管理できます。言語ごとに pyenv・rbenv・nvm……と別々のツールを覚えなくてよくなる、というのが大きな価値です。

移行のハードルが低いのもポイントで、mise は asdf と互換性があります。asdf のプラグインや `.tool-versions` ファイルをそのまま活かせるので、すでに asdf を使っているチームでも乗り換えやすくなっています。

## 2. 環境変数：direnv を別で入れなくていい

開発では「このプロジェクトのときだけ、この環境変数を設定したい」という場面がよくあります。これまでは direnv のような専用ツールを別途入れて、`.envrc` を管理していました。

mise では、バージョン管理と同じ `mise.toml` の中に環境変数を書けます。

```toml
[env]
NODE_ENV = "development"
DATABASE_URL = "postgres://localhost/myapp"
```

これもバージョンと同じく、ディレクトリに入ったときだけ有効になり、出れば元に戻ります。`.env` ファイルを読み込ませることもできるので、既存の運用を大きく変えずに移行できます。

「バージョンも環境変数も同じ1ファイルに書いてある」という状態は、プロジェクトの前提条件が1か所に集まるということです。あちこちのファイルを見て回らなくてよくなります。

## 3. タスクランナー：make と npm scripts の混在をなくす

プロジェクトには「開発サーバーを起動する」「テストを流す」「DB をマイグレーションする」といった、決まりきったコマンドがつきものです。これを Makefile に書く人もいれば npm scripts に書く人もいて、プロジェクトによって場所がバラバラ、ということが起こりがちでした。

mise はタスクランナーも兼ねているので、こうしたコマンドを `mise.toml` に集約できます。

```toml
[tasks.dev]
run = "npm run dev"

[tasks.test]
run = "vitest"
```

```bash
mise run dev
mise run test
```

言語やフレームワークが違っても `mise run xxx` という同じ入口でコマンドを実行できるため、「このプロジェクトのテストってどう動かすんだっけ」と迷う回数が減ります。

## なぜ導入するのか

ここまで機能を見てきましたが、mise の価値が一番効いてくるのは**チーム開発**だと感じています。

これまでのプロジェクトでは、README に「Node 18 を入れてください」「direnv を設定してください」と手順を書き、新しく入ったメンバーがそれを1つずつ手で再現していました。手順が古くなっていたり、書き忘れがあったりすると、環境構築でつまずいてしまいます。

mise を使うと、**バージョン・環境変数・タスクの定義をすべて `mise.toml` に書いてコミットしておくだけ**で済みます。新しく入ったメンバーは、

```bash
mise install
```

と打つだけで、設定ファイルに書かれたツールが一括でインストールされ、全員が同じ環境で開発を始められます。「動く環境」がコードと一緒にリポジトリに入っている状態になるわけです。

自分が mise を知ったのも、チームメンバーが当たり前のように使っているのを見たのがきっかけでした。導入すれば全員の環境がそろい、オンボーディングが速くなる。これが、個人で使うとき以上に効いてくる理由だと思います。

## おわりに

- mise は「バージョン管理・環境変数・タスク実行」の3つを1つにまとめてくれるツール
- ディレクトリに入るだけでツールのバージョンや環境変数が自動で切り替わる
- asdf と互換性があるため、既存環境からの移行もしやすい
- `mise.toml` をコミットしておけば、チーム全員が同じ環境を `mise install` 一発で再現できる

「個人の環境を快適にするツール」であると同時に、「チームの環境をそろえるツール」でもある、というのが使ってみての印象です。まずは1つのプロジェクトに `mise.toml` を置いてみるところから始めてみてください。
